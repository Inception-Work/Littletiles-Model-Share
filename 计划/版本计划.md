## 每轮固定流程

1. **门禁**：确认上一组合获得用户实机「通过」；若失败，留在当前分支修复并重新交付，不能跳号。第一次门禁为 `forge/1.12.2` 当前测试包。
2. **基线**：记录 Git 提交、未提交改动、LT/CreativeCore/加载器/Java 具体版本及官方发布来源。已有改动必须先核对归属，不能因切分支丢失。创建独立 `<loader>/<mc-version>` 分支；同版本不同加载器仍各有独立分支和构建产物。
3. **功能与界面**：以 1.12.2 为参照实现以下项目，不以「能启动」代替功能完成：I 键和命令入口、列表与搜索/筛选/分页、登录与令牌刷新、作品详情/邀请访问码/图片/作者页、收藏与关注（作品/合集分 tab、关注用户与动态）、我的空间（自己的作品/合集）、上传草稿与提交、七种语言、原生 LittleTiles 预览及失败时 OBJ 白模预览、获取蓝图（单人/联机/专服）、页面导航和错误提示。分页只显示页码，不显示作品总数。仅在目标版本 LT API 不支持时记录差异、原因和替代方案，经用户确认后调整验收范围。
4. **验证**：构建、自动检查、游戏内 GUI 截图/交互、真实模型预览（含塔吊等大模型）、登录权限、SNBT 上传和蓝图下载、单人与专服分别测试。编译通过不等于游戏实测通过。
5. **交付**：提供唯一标识 Minecraft 版本及加载器的测试 JAR、所需 LT/CreativeCore 版本、安装及移除旧 JAR 步骤、已知限制。记录构建和测试结果于[经验记录](../经验.md)，标记「待用户测试」。
6. **验收与发布**：收到用户明确「通过」才标记已验收并进入下一行；失败则记录复现和修复。正式发布时提交与构建完全一致的源码，按现有发布流程创建并推送对应 tag，核对远端和下载文件。各版本 tag 必须唯一，不能重用旧 tag。

## 当前阻塞与下一步

- `forge/1.12.2` 的 0.1.4 beta 已发布：源码提交 `a2d6fe6`、文档提交 `aa049f1`，分支与 `v0.1.4` tag 均已推送；网站 `releaseId=5`，下载文件已核对哈希。**仍等待用户实机验收**（收藏/关注、我的空间、大模型预览、上传可见性、联机蓝图）。
- 未收到明确「通过」前，不创建/实施 `forge/1.19.4`；若验收失败，继续在 `forge/1.12.2` 修复并发新版本号，不覆盖 `v0.1.4`。
- 远端默认分支仍是 `main`，`forge/1.12.2` 已作为新分支存在；是否把默认分支切到版本分支需仓库管理员确认，避免直接删除默认分支。
- 每一轮在[经验记录](../经验.md)补充确证事实、失败和回退步骤，不把推测记作验收结论。
